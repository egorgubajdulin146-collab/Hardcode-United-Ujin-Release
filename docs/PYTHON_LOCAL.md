# Java ↔ отдельные Python-эмуляторы (LOCAL)

Опциональный стенд для назначенной учётки и пары UUID каталога. Это не Ujin,
не платформенные SN и не общий публичный демо-аккаунт. Гостевое демо использует
внутренние Java-эмуляторы с отдельными данными.

1. Запустите отдельный Python Compose из infra/emulators/README.md.
2. Войдите в наше приложение и создайте датчик/лампу из шаблонов. Сохраните их
   UUID и локальное правило leak EQ1 → lamp1. Для источника нужно событие CHANGE.
3. В закрытом env задайте UJIN_LOCAL_PYTHON_OWNER (точный логин владельца),
   UJIN_LOCAL_PYTHON_SOURCE_DEVICE_ID и UJIN_LOCAL_PYTHON_TARGET_DEVICE_ID.
   Значения не помещайте в Git. Запускайте одно правило на одну пару.
4. Добавьте infra/emulators/java-overlay.yaml после runtime-overlay:

   ```sh
   docker compose --project-directory . --env-file .env \
     -f infra/compose.yaml -f infra/compose.runtime.yaml \
     -f infra/emulators/java-overlay.yaml up -d --wait
   ```

   Backend подключится к внешней сети ujin-emulators; адреса внутри неё —
   http://leak:8080 и http://light:8080. Порты 18191/18192 — только localhost
   хоста, а localhost внутри backend означает сам backend-контейнер.
   Без overlay интеграция выключена. Для Java на хосте можно задать
   UJIN_LOCAL_PYTHON_ENABLED=true и loopback URL соответствующих процессов.

## Публичный сервер и автоматический deploy

Назначайте пару обычному тестовому аккаунту, не гостю. Создайте отдельные
датчик/лампу и правило, чтобы не менять исполнитель уже используемых устройств.
Три значения OWNER/SOURCE_DEVICE_ID/TARGET_DEVICE_ID храните в закрытом
`/etc/ujin/local.env` (600), не в release archive и не в Git.

Оператор устанавливает проверенный `infra/emulators/java-overlay.yaml` как
root-owned `/etc/ujin/python-local.yaml` (600). Receiver автоматически добавляет
этот файл после штатных трёх Compose-файлов при каждом deploy. Сам receiver
нужно обновить отдельно в `/usr/local/sbin/ujin-deploy-receive`: merge не
переустанавливает его автоматически. Загружаемый артефакт не может подменить
операторский overlay. При отсутствии файла поведение не меняется.

Первое включение требует backup, общего `/run/lock/ujin-deploy.lock`, текущих
image SHA и прежнего Compose project/volume. Используйте `up --no-build`,
не пересобирайте старый тег и не выполняйте `down --volumes`. Backend при
добавлении сети пересоздаётся, поэтому пользователям понадобится войти снова.
Сначала убедитесь, что сеть `ujin-emulators` и оба Python-процесса healthy.

Для отключения под тем же lock уберите операторский overlay из конфигурации
и пересоздайте только backend штатными файлами; Python-state автоматически
не переносится во внутренний Java-state. Сначала выключите назначенное правило,
чтобы смена исполнителя не вызвала неожиданное действие. Непроверенный старый
резерв без Python-адаптера запускать с этим overlay нельзя.

## Проверка

Откройте источник в LOCAL: панель явно показывает «Внешний LOCAL-Python».
Измените leak через штатный POST /stimuli Python-процесса (см. README эмуляторов),
нажмите «Проверить показание Python». Это ручная проверка. Для повторных проверок включите «Наблюдать Python, пока открыта карточка»: запросы идут последовательно через 3 секунды после завершения предыдущего. При закрытии карточки/выходе наблюдение прекращается; скрытого серверного расписания нет.
Первое наблюдение при отсутствии сохранённого source-state устанавливает baseline
без действия. Если у устройства уже есть сохранённый LOCAL-state, он используется
как предыдущий baseline; подключайте свежую пару либо заранее выровняйте значения.

После baseline0 измените leak на1 и снова проверьте. Java обрабатывает сохранённое
правило, резервирует PENDING и отправляет lamp в Python вместо изменения внутренней
Java-лампы. Только успешный POST и отдельный GET /state с ожидаемым значением
подтверждают команду и переводят Run в SUCCEEDED. Повтор eventId не читает источник
заново, одинаковое значение не повторяет действие. Состояние/события/квитанции
сохраняются в БД; Python после собственного restart сбрасывается в0.

Внутренние WET-кнопки для назначенного Python-источника недоступны: иначе они
меняли бы Java-состояние вместо Python. Команда лампе в обычной LOCAL-панели
направляется адаптером в Python; дополнительные сигналы этой лампы не поддержаны.
Нельзя одновременно использовать внутренний Java и Python как исполнителя одной
и той же назначенной лампы.

## API и неопределённость

- POST /api/v1/local-python/poll, тело {"eventId":"UUID"}; owner только из сессии,
  source/target/адреса только из серверной настройки. Нужны вход и CSRF.
- GET /devices/{uuid}/state?mode=LOCAL для назначенной пары читает реальный Python
  state и возвращает provider=PYTHON; время observedAt — время backend-чтения.
- Обычный POST /devices/{uuid}/commands с executionMode=LOCAL для назначенной
  лампы резервирует команду и направляет её в Python.
- POST /api/v1/local-python/commands/{commandId}/check — только чтение результата,
  без повторной отправки POST /command.
- POST /api/v1/local-python/events/{eventId}/check проверяет результаты действий события только чтением, без повторных команд.
- Сценарный commandId совпадает с runId, что связывает квитанцию с журналом.

Потерянный ответ POST оставляет UNKNOWN: старое совпадающее значение не доказывает
исполнения. Если ACK получен, но readback временно недоступен/не совпал, явная
проверка может подтвердить последующее состояние. Автоматического resend нет.
Прерванный DISPATCHING через15с при явной проверке становится UNKNOWN.
Неизвестное/missing состояние не превращается в0; другой владелец не получает
доступ к этой паре. Локальная сериализация poll рассчитана на один backend,
многорепличный запуск общего Python-стенда не поддержан.

Не публикуйте Python-порты через Nginx. Они предназначены доверенному оператору.
Принимаются только фиксированные серверные HTTP-адреса loopback/leak/light;
URL из запросов пользователя не используются. Токен Ujin адаптеру не нужен.
