# Доставка команд UJIN до эмулятора

Команда `executionMode=UJIN` отправляется на платформу документированным
методом `apartment/send-signal` (параметры `token`, `serialnumber`, `signal`,
`value`; POST form), платформа кладёт задачу в очередь `task`/`task_dt`
устройства. Исполнение подтверждается только применением задачи к локальному
Java-эмулятору и последующей публикацией фактического состояния.

`HTTP 200/error=0` означает **приём запроса платформой**, а не исполнение:
квитанция остаётся `PENDING` с причиной `ACCEPTED_AWAITING_APPLY`.

## Флаг (по умолчанию выключен)

```yaml
ujin:
  commands:
    enabled: false              # выключено по умолчанию: ничего не отправляется
    task-fetch-enabled: false   # источник задач — только с подтверждёнными правами
    task-signal-prefix: ""      # подтверждённый полный префикс имён словаря
    observation-window-seconds: 15
```

С выключенным флагом `POST /devices/{id}/commands` с `executionMode=UJIN`
отвечает `503 COMMAND_DELIVERY_DISABLED`, а статус интеграции показывает
downlink `BLOCKED` с этой причиной. LOCAL-команды работают как раньше.

## Статусы квитанции команды

| Статус | Когда выставляется |
| --- | --- |
| `PENDING` | Команда сохранена до внешнего вызова; платформа приняла запрос |
| `CONFIRMED` | Только после применения новой задачи `task/task_dt` к эмулятору |
| `FAILED` | Платформа явно отказалась (Access denied, ошибка платформы, неверная роль) |
| `UNKNOWN` | Сетевая неопределённость: таймаут/обрыв после отправки, повреждённый ответ |

Повтор того же `commandId` с тем же payload возвращает прежнюю квитанцию без
новой отправки; с иным payload — `409 IDEMPOTENCY_CONFLICT`. Автоматического
повтора при `UNKNOWN` нет. `POST /commands/{id}/check` опрашивает задачи и
оценивает результат; после истечения окна наблюдения (наша настройка, не SLA
Ujin) неизвестный результат становится `UNKNOWN` (`OBSERVATION_WINDOW_EXPIRED`
или `TASK_SOURCE_BLOCKED`).

Старое совпавшее значение состояния не доказывает исполнение команды.
`POST /commands/{id}/resolution` только отмечает `ACKNOWLEDGED_UNKNOWN` с
заметкой: статус остаётся `UNKNOWN`, повтор команды не выполняется, удержание
удаления устройства снимается.

## Задачи платформы (task / task_dt)

Задокументированный источник задач — `bmsdevice/get-device-info`
(`data.signals[].task`, `signal_task_dt`; виден только для `mgmt != r`).
Исторически резидентский токен получает на нём `Access denied`; перебор ролей
и обходные пути не используются. До письменного подтверждения организаторами
разрешённого пути/роли источник остаётся выключенным (`task-fetch-enabled`),
а `check` честно отвечает `TASK_SOURCE_BLOCKED` без подтверждения исполнения.

Когда источник разрешён, применяются только точные соответствия из привязки:
имя задачи равно `platformName` или `подтверждённый префикс + platformName`.
Дедуп по `task_dt` записывается **после успешного применения**; повтор того же
`task_dt` не исполняется дважды, неуспешное применение не помечает задачу.
Секреты, токены и полные URL с query в логи не попадают.

Не подтверждённые транспорты доставки (HTTP-callback `device_first_server`,
WebSocket cast) не реализованы и остаются `BLOCKED`.

## Уточнение review: история задач и исходная очередь

Перед отправкой при включённом task-fetch снимается исходная очередь задач.
Совпадающий с исходной очередью task_dt не подтверждает новую команду.
При недоступном исходном снимке подтверждение по задаче не выставляется;
отказ preflight не вызывает отправку команды. Это наблюдение очереди, а не
доказанная end-to-end корреляция по uniq; live-приёмка всё ещё требуется.

История всех успешно применённых task_dt хранится в PostgreSQL (V7), поэтому
после A → B повтор A тоже отклоняется, в том числе после рестарта.
Отсутствующий task_dt не заменяется ключом из значения: такая задача отклоняется.
Прерванная DISPATCHING после окна наблюдения становится UNKNOWN без повторной
отправки. Поздний сетевой ответ не снимает UNKNOWN или пользовательскую отметку.
