# Контракт первого сценария — 0.1.2-draft

Статус: **DRAFT, требуется совместное review frontend/backend**. Это проект
API приложения, не описание уже работающего backend и не копия API платформы Ujin.
Все примеры синтетические; результаты исполнения и проверки стенда отсутствуют.

- [OpenAPI 3.0.3](openapi.json) — маршруты, тела, ответы, ошибки.
- [Примеры](examples.json) — согласованные между собой данные для обсуждения,
  будущих frontend-моков и QA. Моки не являются реализацией платформы.

## Граница MVP

Предложен путь: датчик `leak` → условие `leak EQ 1` → `lamp=1` на устройстве
`light` → наблюдаемое состояние и журнал. Режимы LOCAL и UJIN разделены.
Число устройств и этот сценарий — выбор для первого пути, а не заявление,
что все остальные требования конкурса уже закрыты.

В первой версии редактор — форма выбора устройства, сигнала, значения и действия.
Drag-and-drop, расписания, несколько условий/действий и все девять семейств
не входят в этот срез. Прежде реализации объём нужно подтвердить.

## Декларации и значения

Устройство имеет UUID приложения, название, семейство и сигналы с уникальными
внутри устройства ключами. Группы: property/capability/setting; management:
r/rw/w. Поддерживаемый тип значения первого среза — NUMBER; бинарные сигналы
передаются числами 0/1, а не строками и не JSON boolean.
Не делать вывода, что вся платформа поддерживает только числа.

- `property` требует `management=r`, `capability` — rw/w, `setting` — rw.
- Непустое название, уникальные ключи; min ≤ max; допустимы только конечные числа.
- При наличии enumValues значение должно входить в список, а не только в диапазон.
- Источник триггера читаемый (r/rw), действие управляемое (rw/w).
- Для сравнения и действия валидируются тип/диапазон/enumValues исходного сигнала.
- Нельзя незаметно изменить сигнал, на который ссылается правило: 409
  DEVICE_IN_USE; в первом срезе переименование/изменение такой декларации
  отложено до обновления зависимых правил.
- Семейство custom может иметь описание, но его физика не появляется автоматически:
  запуск неизвестного эмулятора — 422 FAMILY_UNSUPPORTED, а не ложный успех.

UUID приложения не равен serialnumber или ext_guid Ujin. Платформенный
serialnumber хранить строкой: он может быть больше безопасного integer JavaScript.
Backend хранит отдельно serialnumber/ext_guid/model/class/apartment_id и доступы;
публичный DTO устройства отдаёт только platformLink (состояние привязки).
Значения credentials не включаются в декларации, OpenAPI, frontend или журналы.

## Проход по API

1. GET `/api/v1/system`: версия контракта и фактически доступные режимы.
2. POST `/api/v1/devices`: сохранить две декларации, получить UUID/version.
   GET списка/карточки и PUT с expectedVersion обеспечивают повторное открытие.
3. GET `/api/v1/devices/{deviceId}/state?mode=LOCAL`: состояние эмулятора.
   Команда в управляемый сигнал — POST `.../commands`, затем GET
   `/api/v1/commands/{commandId}` до подтверждения/ошибки.
4. POST `/api/v1/scenarios`: правило с trigger, action, enabled и executionMode.
   GET и PUT карточки обеспечивают открытие/редактирование и включение/выключение.
   PUT — полная замена данных правила плюс expectedVersion; stale version → 409.
5. В LOCAL POST `/api/v1/devices/{leakId}/stimuli` с kind=WET и value=1
   задаёт физическое воздействие. Адаптер должен вызвать `set_wet`, выполнить
   согласованный шаг эмуляции и получить событие `leak=1`.
   Прямой командой в read-only `leak` это делать нельзя (422 SIGNAL_READ_ONLY).
6. Stimulus возвращает 202, eventId и статус ACCEPTED. Принято ≠ исполнено.
   GET `/api/v1/events/{eventId}` возвращает PROCESSED/FAILED и runIds.
7. GET `/api/v1/runs?eventId=...` и GET карточки запуска показывают вход,
   проверку условия, действие, результат/ошибку и режим. PROCESSED события
   означает завершение его обработки; успешность действий определяется статусами runs.

Воздействие WET разрешено только для локального leak-эмулятора. На другом
семействе — 422 STIMULUS_UNSUPPORTED. Стимулы не направляются в реальное
оборудование и не используются как скрытый способ записи read-only сигналов.

Начальное состояние: датчик сухой (leak=0), свет выключен (lamp=0),
brightness=100, offline_timeout=0. Для повторного демо — WET=0,
явная LOCAL-команда lamp=0, новое eventId для следующего воздействия WET=1.
Если значение leak не изменилось, нового события изменения нет: event receipt
PROCESSED с пустым runIds. Телеметрия батареи не запускает правило для leak.

## Исполнение, повторы и сохранение

- Сценарий задаётся одним источником, EQ и одним действием. Цикл/ссылка
  на тот же управляемый сигнал не принимается как безопасный первый сценарий:
  422 SCENARIO_CYCLE. Глубокие цепочки в этом срезе не поддерживаются.
- Изменения деклараций и сценариев сохраняются. Версия сценария фиксируется
  в запуске; последующее редактирование не изменяет старый результат.
- При проверке правила для подходящего источника создаётся журнал запуска.
  Выключенное правило → SKIPPED / SCENARIO_DISABLED; условие ложно →
  SKIPPED / CONDITION_FALSE. Другой источник не создаёт запуск этого правила.
- Статусы: PENDING — действие ещё не подтверждено; SUCCEEDED — состояние
  назначения подтверждено; FAILED — известная ошибка; BLOCKED — нет нужной
  интеграции/права; UNKNOWN — после прерывания неизвестно, произошло ли действие.
- Пара (scenarioId,eventId) уникальна. Повтор того же события не исполняет
  действие ещё раз, даже если после него отредактирован сценарий.
- Повтор stimulus eventId или commandId с тем же телом возвращает прежний
  receipt, с другим телом/устройством — 409 IDEMPOTENCY_CONFLICT.
  Ключи и результат должны переживать restart. Срок хранения и очистку
  ключей согласовать до включения удаления журналов.
- Без атомарной гарантии исполнителя не обещать exactly-once внешнему устройству.
  После сбоя неопределённое действие не повторять автоматически с новым ID;
  сохранить UNKNOWN и сверить состояние. Тест restart обязателен.
- Локальные сигналы остаются 0/1. wire-обход 0→0.001 применяется только
  в адаптере Ujin по подтверждённому маппингу; нельзя превращать epsilon в true.
- Журнал и режимы определяются backend. UI не создаёт SUCCEEDED сам и не
  меняет режим при отказе Ujin автоматически.

## Ujin: честная граница

GET `/api/v1/integrations/ujin/status` показывает отдельно publish/read/downlink/
autoscripts: UNKNOWN, AVAILABLE либо BLOCKED, причину и время фактической проверки,
если она была. AVAILABLE — лишь возможность, не результат конкретной команды.
Публикация значения не доказывает полный downlink или исполнение autoscript.

Для UJIN-запуска обязательны привязанные устройства и фактически поддержанные
возможности. При отсутствии — 503 INTEGRATION_UNAVAILABLE до выполнения команды.
При потере подтверждения после отправки — PENDING/UNKNOWN в журнале, не success.
Платформенная публикация/чтение/команда и локальная цепочка должны иметь
раздельные доказательства. Точный адаптер внешнего API этим документом не утверждается.

## Ошибки и списки

400 — синтаксис/форма запроса; 404 — нет ресурса; 409 — версия, ID-повтор
с другим телом или используемая декларация; 422 — несовместимая семантика;
503 — нужная интеграция недоступна. Формат `application/problem+json`:
type/title/status/code/detail, необязательный errors с field/message.
Без stack trace, URL с token и секретов. Ошибки платформы переводятся в этот
контракт, а не возвращаются браузеру целиком.

Списки: page≥0, size=20 по умолчанию (1–100), items/page/size/total.
Сортировка: устройства/правила по id ASC, запуски по createdAt DESC, id ASC.
Необязательные фильтры запусков — eventId, scenarioId.

## Что нужно подтвердить до реализации/деплоя

1. Общий review API/примеров backend и frontend; это пока предложение.
2. Ровно этот сценарий, два устройства, numeric/EQ и сохранение — объём первого среза.
3. Семантика restart, дедупликации, состояния эмуляторов и границы каскадов.
4. Авторизация пользователей приложения и разрешения на команды/редактирование/
   локальные стимулы. API не определяет готовую схему входа: до её согласования
   допускается только изолированный локальный демо-доступ, не внешний стенд.
   401/403 в OpenAPI резервируют ошибки; они не означают реализованную защиту.
5. Фактические возможности Ujin. Backend использует Java 25 и Gradle Wrapper;
   контракт не меняет имеющийся каркас и не требует перехода на Maven.

Отдельных unit/интеграционных/браузерных прогонов и платформенного QA по этому
документу пока нет. Совпадение примеров со схемой не является приёмкой приложения.

## Уточнения 0.1.1-draft перед повторным review

### Удаление устройств

GET `/api/v1/devices/{deviceId}/dependencies` показывает scenarioIds (включая
выключенные правила) и pendingOperationIds. Это снимок, не гарантия последующего
удаления. DELETE карточки требует expectedVersion; сервер в одной транзакции
повторно проверяет версию, правила и незавершённые операции.

- 204: локальное описание/состояние удалены, больше не выдаются; повтор — 404.
- 409 VERSION_CONFLICT: версия изменилась.
- 409 DEVICE_IN_USE: есть зависимые правила или неразрешённые PENDING/UNKNOWN операции;
  force и неявный каскад не предусмотрены.
- Перед удалением нужно явно изменить зависимые правила через PUT так, чтобы
  они ссылались на другие устройства, и разрешить незавершённые операции.
  Одного выключения правила недостаточно. Удаление сценариев отдельным API
  не входит в текущий срез.
- Удаление из приложения не вызывает hide/delete в Ujin. Такая разрушительная
  операция платформы этим контрактом не предусмотрена.
- Исторические журналы сохраняют снимок входов/действий и идентификатор удалённого
  устройства; UI обозначает его как удалённое, не теряет старое доказательство.

### События как часть декларации

Устройство теперь явно содержит events; пустой массив допустим, но такое
устройство нельзя выбрать источником правила. EventDefinition содержит key,
title, signalKey и emission=CHANGE. Ключи событий уникальны внутри устройства,
signalKey ссылается на читаемый объявленный сигнал. Для первого среза событие
возникает при изменении значения; расписания/произвольные события вне этого среза.

Trigger содержит eventKey и signalKey; сервер проверяет, что событие ссылается
именно на этот сигнал. Пример: leak_changed → leak. Название, signalKey и eventKey
не взаимозаменяемы. Команды и настройки продолжают описываться management/group.
Изменение/удаление используемого события запрещено с DEVICE_IN_USE.

### Недоступность устройства

DeviceState отдельно сообщает availability=ONLINE/OFFLINE/UNKNOWN.
Если источник OFFLINE/UNKNOWN, новое воздействие или команда не принимается как
успешное: 409 DEVICE_OFFLINE либо DEVICE_AVAILABILITY_UNKNOWN. Если назначение
правила недоступно, запуск FAILED с соответствующей причиной; команда не отправляется.
Если связь пропала после отправки и исход неизвестен, запуск UNKNOWN, не FAILED
с автоматическим повтором. Недоступность платформы остаётся отдельным 503.
После восстановления нельзя повторять прежнее событие под новым ID без решения
оператора. Недоступное устройство остаётся видимым, правило не удаляется.

Это обновление меняет draft-схемы и требует повторного review: прежнее одобрение
0.1.0-draft не подтверждает новые поля/операции. Проверки удаления: нет зависимостей,
выключенное зависимое правило, pending/unknown действие, stale version, гонка создания
правила с удалением, повтор DELETE и сохранение истории. Все runtime-проверки NOT RUN.


## Разрешение UNKNOWN — 0.1.2-draft

Неопределённый исход не должен навсегда блокировать удаление устройства.
POST `/api/v1/commands/{commandId}/resolution` и
POST `/api/v1/runs/{runId}/resolution` принимают непустую `note` оператора.
Операция разрешена только для UNKNOWN и требует права управления командами,
когда авторизация настроена; до её согласования действует только изолированное
локальное демо. PENDING нельзя закрыть этим способом: сначала исполнитель
должен завершить ожидание либо зафиксировать UNKNOWN по таймауту.

Сервер атомарно сохраняет `resolution` с kind=ACKNOWLEDGED_UNKNOWN,
заметкой и серверным resolvedAt, снимая только блокировку удаления этой операции.
Статус остаётся UNKNOWN: принятие неопределённости не доказывает успех или отказ.
Связанные run/command разрешаются вместе; остальные операции и любые ссылки
сценариев продолжают блокировать удаление. Receipt и аудит переживают restart.
Событие, команда и правило повторно не исполняются, обращения к Ujin не выполняются.

200 возвращает receipt/run с resolution; повтор с той же заметкой возвращает
сохранённый результат без нового времени/действия. Другая заметка после разрешения
или исходный статус не UNKNOWN — 409 RESOLUTION_CONFLICT. Отсутствующий ID — 404;
пустая/пробельная заметка — 422. Заметка и время неизменяемы. Если до разрешения
пришло подтверждение и статус изменился, атомарная проверка отклоняет запрос с 409.
Поздние подтверждения после разрешения сохраняются как отдельные записи аудита,
не переписывают принятое UNKNOWN и не возвращают блокировку удаления.

GET dependencies исключает разрешённые UNKNOWN из pendingOperationIds.
UI показывает «исход неизвестен, закрыто оператором», заметку и время; кнопка
не называется «подтвердить успех». Удаление устройства сохраняет этот аудит.
Проверки: UNKNOWN → разрешение → отсутствие операции в dependencies; PENDING
отклоняется; повтор/конфликт заметки; связанные run/command; другая операция
и выключенный сценарий по-прежнему блокируют DELETE; гонка с подтверждением;
restart и позднее подтверждение после удаления. Runtime-проверки NOT RUN.


## Сессионный адаптер Ujin

В OpenAPI отдельно описаны GET `/api/auth/csrf`, POST `/api/auth/login`,
POST `/api/auth/logout` и GET `/api/v1/ujin/devices/{serialnumber}/signals?name=…`.
Клиент сохраняет cookies; тело GET csrf передаёт в `X-XSRF-TOKEN` при POST.
Перед logout следует получить csrf заново. Пароль используется при входе,
токен Ujin хранится только в серверной сессии. Cross-origin/CORS здесь не согласованы.

Адаптер возвращает `{name, value}`, где value — строка даже для чисел/boolean.
Это отдельный DTO, не числовой SignalValue и не реализация `/devices/{deviceId}/state`.
Подключение frontend к этому DTO остаётся PENDING до отдельного согласования.

HTTP 401/403 upstream распознаются как явные отказы; неизвестный JSON error
и некорректный ответ дают 502, ошибки соединения/таймаут — 503.
Коды авторизации внутри JSON Ujin не подтверждены и не угадываются.
Ошибки не содержат upstream body, credentials или URL с токеном.
