# Демонстрация и финальная приёмка

Это инструкция ожидаемых действий, не отчёт об успешном прогоне.
Для публичного показа сначала зафиксируйте фактическую версию стенда и результаты.
Команды ниже по смыслу относятся к LOCAL-эмуляторам. Они не доказывают управление
реальным оборудованием. Запись в Ujin требует отдельно разрешённого теста.

## Подготовка

1. Откройте стенд и войдите своей тестовой учётной записью. Не показывайте
   пароль, cookies, токены и файл доступов в записи экрана.
2. Используйте источник API. Демо/MOCK показывает синтетические данные.
3. Создайте свои устройства из шаблонов «Датчик протечки» и «Сигнальная лампа».
   Не редактируйте чужие данные. Если каталог пуст, это нормально для новой
   учётки: устройства Ujin автоматически не импортируются.
4. Создайте одно включённое локальное правило по [README](../README.md).
   На этой паре не должно быть других включённых правил, меняющих ту же лампу.
5. Убедитесь, что оба эмулятора ONLINE. Установите лампу в 0, затем датчик в 0.
   Состояние каждого устройства проверяйте в его панели, а не только по toast.

## Основной показ — около двух минут

| Время | Что показать | Проверяемый результат |
| --- | --- | --- |
| 0:00–0:20 | Декларацию датчика и лампы | Показание протечки доступно для чтения, свет — для управления; диапазон 0/1 |
| 0:20–0:40 | Сохранённый сценарий | «Когда изменится протечка, если протечка = 1, включить свет»; режим локальный |
| 0:40–1:00 | «Обнаружить воду» после исходного 0 | Новое событие, лампа становится 1 |
| 1:00–1:20 | Ссылку на журнал этого события | Вход, решение, действие и результат; SUCCEEDED для локального действия |
| 1:20–1:40 | Повтор «Обнаружить воду» без возврата в 0 | NO_STATE_CHANGE, без нового исполнения действия |
| 1:40–2:00 | Статус интеграции и границы прототипа | LOCAL и Ujin различимы; недоступный канал не выдан за успешную интеграцию |

Это ориентир длительности, готового видео и результатов защиты ещё нет.

## Дополнительные проверки перед сдачей

- Выключите правило, верните лампу в 0, сделайте переход датчика 0→1.
  Ожидается SCENARIO_DISABLED, лампа остаётся 0.
- Включите правило, переведите лампу OFFLINE, сделайте 1→0→1.
  Ожидается BLOCKED / DEVICE_OFFLINE. Верните ONLINE и повторите 1→0→1:
  новое действие может выполниться; повтор того же значения не является повторным запуском.
- Во второй отдельной сессии проверьте, что UUID устройства/сценария/журнала
  первого аккаунта недоступны. Сам UUID не является разрешением доступа.
- Перезапуск и rollback проверяйте в отдельном контуре с резервной копией:
  сохранность устройств, правил, состояний, квитанций, истории задач и запретов A/B.
  Не перезапускайте публичный стенд ради показа без согласованного окна.
- После проверки выключите созданное тестовое правило и зафиксируйте остаток.

## Что отдельно доказывает реальную интеграцию

1. Явная привязка устройства нашего каталога к назначенному SN, без подстановки UUID.
2. Реальное предметное показание в карточке. Служебный `ver` подтверждает только
   работу чтения; missing signal нельзя заменять нулём или демо-значением.
3. Публикация с отдельным чтением результата. HTTP 200 / error=0 недостаточно.
4. Доставка команды до эмулятора и новое подтверждённое применение задачи.
   PENDING и UNKNOWN не означают исполнения; автоматический resend запрещён.
5. Для сценария по Ujin — отдельная приёмка наблюдения и связанного Run/command.
   Наличие локального сценария этот пункт не закрывает.

Вход employee/BMS и вход резидента проверяют разные возможности Ujin.
Учётка сотрудника не делает пользователя администратором нашего приложения.
Не переключайте роли или credentials, чтобы обходить отказ доступа.

При блокере запишите метод, HTTP-статус, нормализованный код, время и версию.
Не включайте в отчёт секреты, полный URL с query или чужие персональные данные.
