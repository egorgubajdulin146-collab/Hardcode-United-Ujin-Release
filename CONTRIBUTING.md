# Работа с репозиторием

## Рабочее изменение

1. Сверить задачу и критерии приёмки. Пока кейса нет, не добавлять предметные
   функции и не переносить реализацию предыдущего продукта.
2. Выполнить `git fetch origin`, проверить рабочее дерево и изменения коллег.
3. Создать предметную ветку от актуального `origin/develop`:
   `feat/...`, `fix/...`, `docs/...` или `infra/...`.
4. Внести одно законченное изменение и выполнить относящиеся к нему проверки.
5. Перед каждым commit/push снова обновить refs и проверить diff.
   Перед коммитом проверить `git var GIT_AUTHOR_IDENT` и
   `git var GIT_COMMITTER_IDENT`. Не менять чужое авторство.
6. Открыть PR в `develop`. Описание — коротко от первого лица:
   «Добавил… Проверил… Осталось…». Невыполненные проверки отметить явно.
7. После review исправлять тот же PR. Не использовать force push,
   не удалять чужие изменения и не выполнять merge без согласованного права.

Замечания к открытому PR писать в нём. GitHub Issues для правок не используем.
Замечания вне открытого PR передавать ответственному участнику в согласованном
командном процессе, не публикуя приватную переписку в продукте.

## Итоговый проект

Финальный PR направляется из `develop` в `main`. До его merge должны быть:

- выполнены требования кейса и проверен основной пользовательский сценарий;
- пройдены применимые сборки, тесты и проверки миграций;
- выполнен запуск на чистом окружении по README;
- проверена фактическая версия стенда, если он требуется;
- перечислены известные ограничения и подготовлены материалы защиты;
- назначен ответственный за финальный merge.

Не считать наличие веток настройкой CI или защиты GitHub: обязательные
проверки и права merge согласуются отдельно. Публикация в `main` не равна деплою.

Секреты, локальные рабочие материалы и чужие персональные данные в Git не добавлять.
Обязательные лицензии и сведения об использованных компонентах сохранять.
